# Эксперимент: зазор ACK → ClientHello и то, что видит сервер

Проверяем два утверждения, которые легко перепутать:

1. разницу между завершением TCP-рукопожатия и первым байтом TLS `ClientHello`
   можно читать как RTT до клиента или как «лишний хоп»;
2. если на машине стоит локальный TUN-прокси, сервер всё равно видит «ваш» TCP-стек.

Оба утверждения неверны. Ниже — измерения.

Дата: 2026-11-18. Скрипты: [harness.py](harness.py), [probe.py](probe.py).
Сырые логи: [raw/](raw/).

## Часть 1. Зазор на контролируемом стенде

### Стенд

`harness.py` поднимает на одном Linux-хосте четыре TCP-эндпоинта, которые
принимают соединение, запоминают момент возврата `accept()` (финальный ACK
рукопожатия) и ждут первый байт приложения — первый байт `ClientHello`:

| Эндпоинт | Как к нему приходят | Прокси |
|---|---|---|
| `:9443` | напрямую | — |
| `:9444` | через CONNECT-прокси `:9080` | наивный CONNECT, релеит байты |
| `:9445` | через SOCKS5-прокси `:9180` | наивный SOCKS5 без UDP |
| `:9446` | через CONNECT-прокси `:9280` | CONNECT + задержка 150 мс **после** upstream-connect |

Клиент (`probe.py`) делает один и тот же HTTPS-запрос четырьмя путями по 40 раз.
Цель закрывает соединение после первого байта, поэтому curl завершается
TLS-ошибкой — это ожидаемо, измеряются только серверные метки времени.

Два варианта сети:

- **loopback** — клиент, прокси и цель на одном хосте, RTT порядка 0.05 мс;
- **netns** — клиент в изолированном network namespace, соединён с хостом через
  veth, на обе стороны навешен `tc netem delay 10ms`; RTT ≈ 20 мс. Клиентский
  `curl --write-out time_connect` в этом прогоне — 20.28 мс, то есть путь
  действительно эмулирует 20 мс.

Задержка в «медленном» CONNECT-прокси сделана **после** того, как прокси открыл
соединение к цели: сервер уже сделал `accept()`, но ещё не получил `ClientHello`.
Так выглядит обработка на прокси (буферизация, логирование, ожидание), а не
сеть.

### Результаты

Медианы по 40 прогонам, миллисекунды; в скобках — p10–p90.

| Путь | RTT на пути | direct | CONNECT | SOCKS5 | CONNECT + 150 мс |
|---|---|---|---|---|---|
| loopback | ≈ 0 | **2.13** (2.10–2.17) | **2.24** (2.13–2.36) | **2.15** (2.06–2.23) | **152.60** (152.56–152.72) |
| netns + netem | 20 мс | **2.10** (2.05–2.17) | **22.24** (22.20–22.31) | **22.31** (22.17–22.37) | **172.80** (172.69–172.88) |

Полные агрегаты (`n`, min, p10, median, mean, p90, max) — в
[raw/loopback/summary.json](raw/loopback/summary.json) и
[raw/netns/summary.json](raw/netns/summary.json). Ошибок в обработке соединений
не было: на каждый путь по 40 записей `gap_ms`.

### Что это показывает

- **Прямое соединение не измеряет RTT.** Зазор ≈ 2.1 мс и при RTT 0, и при
  RTT 20 мс: TLS-клиент отправляет `ClientHello` сразу за ACK, сервер получает
  его почти одновременно с завершением рукопожатия. В зазор попадает в основном
  подготовка `ClientHello` в TLS-стеке клиента и планировщик, а не сеть.
- **Прокси добавляет примерно один RTT клиент↔прокси.** На пути 20 мс зазор
  вырос до 22 мс: прокси сначала получает CONNECT/SOCKS-запрос, затем открывает
  upstream, отвечает клиенту, и только потом клиент начинает TLS. Это
  «клиентское плечо», а не «ещё один хоп».
- **Тот же зазор можно получить обработкой.** Задержка 150 мс после
  upstream-connect (сеть не менялась) дала 172.8 мс — ровно на 150 мс больше.
  Сервер не может отличить «прокси в 150 мс от клиента» от «прокси, который
  150 мс буферизует/логирует/ждёт». А CONNECT и SOCKS5 в этом стенде дали
  практически одинаковый зазор, хотя устроены по-разному: по величине зазора
  нельзя судить и о типе прокси.
- **Топологию зазор не восстанавливает.** Он говорит «здесь есть посредник или
  очень медленный TLS-стек», но не говорит, где посредник, сколько их и каков
  реальный RTT клиента. Это эвристика «сеть не сходится», а не измерение RTT.

### Ограничения

- Прокси — наш собственный минимальный код, а не продакшен-реализация: без
  аутентификации, DNS, сжатия и TLS-инспекции. Другие реализации могут дать
  другие цифры обработки.
- Эмуляция сети — `netem` в netns, а не реальный WAN: нет потерь, ретрасмитов,
  асимметрии и middlebox'ов.
- `ClientHello` не доходит до завершения TLS: цель закрывает соединение после
  первого байта. Это не влияет на зазор, но исключает эффекты TLS-сессии.
- Один Linux-хост, одно ядро (5.15.0-198), один клиент curl (8.13.0 на Windows,
  7.81.0 на VPS; прогоны в netns — curl 7.81.0).

## Часть 2. Что видит сервер, если на клиенте TUN-прокси

Отдельный захват: клиент — живая **Windows 10 Pro 19045**, на машине запущен
**tun2socks (AmneziaVPN)**, трафик выходит через G-Core Labs (AS199524, Токио).
Клиент делает обычный `curl` на тестовый Linux-сервер; на сервере — `tcpdump`
по SYN. Клиентский `time_connect` — около 2 мс, а TTFB — около 1.4 с: TCP
рукопожатие завершено локально, реальный путь длиннее.

Сервер увидел (IP заменены на документационные):

```
203.0.113.10.4783 > 198.51.100.20.9443: Flags [S], ttl 44,
    win 42340, options [mss 1460,sackOK,TS val ...,nop,wscale 11], length 0
```

Разбор: `Initial TTL 64` (64 − 20 хопов = 44), окно `42340` = 29 × 1460,
`WS 11`, `MSS 1460`, опции `MSS, SACK, TS, NOP, WS`, то есть JA4T
`42340_2-4-8-1-3_1460_11`. Это **ровно** TCP-подпись антипримера из
[§11](../../docs/4-checks/11-stands.md), хотя клиент — Windows, а не Linux:
сервер видит стек выхода туннеля, а не стек клиентской ОС. Локальный TUN-прокси
терминирует TCP так же, как удалённый HTTP-прокси, — только незаметнее.

Отсюда практическое следствие: снять SYN именно Windows-ядра на такой машине
нельзя — TCP держит tun2socks. Для этого нужен хост без локального TUN (эталон
со Starlink в §11) либо отключённый на время прогона TUN; это следующий шаг,
а не результат этого эксперимента.

Сырой вывод захвата (с замазанными IP) — [raw/windows-tun2socks-syn.txt](raw/windows-tun2socks-syn.txt).

## Как воспроизвести

### Loopback

```bash
python3 harness.py --outdir results &
python3 probe.py --host 127.0.0.1 --iterations 40 --out results/client.csv
kill %1
```

### netns с RTT 20 мс

```bash
ip netns add hpdcli
ip link add veth-hpd type veth peer name veth-cli
ip link set veth-cli netns hpdcli
ip addr add 192.0.2.1/24 dev veth-hpd && ip link set veth-hpd up
ip netns exec hpdcli ip addr add 192.0.2.2/24 dev veth-cli
ip netns exec hpdcli ip link set veth-cli up
ip netns exec hpdcli ip link set lo up
tc qdisc add dev veth-hpd root netem delay 10ms
ip netns exec hpdcli tc qdisc add dev veth-cli root netem delay 10ms
python3 harness.py --outdir results-netns &
ip netns exec hpdcli python3 probe.py --host 192.0.2.1 --iterations 40 \
    --out results-netns/client.csv
kill %1
ip netns del hpdcli && ip link del veth-hpd
```

### Захват SYN

На сервере:

```bash
tcpdump -i any -nn -vvv -s0 'tcp port 9443 and tcp[tcpflags] & tcp-syn != 0'
```

На клиенте — любое TCP-соединение к серверу (`curl http://SERVER:9443/`).
Для чистого SYN нужен клиент без локального TUN-прокси.
