# §14. IPv6 и dual-stack: вторая семья адресов как вторая утечка

<sub>[Главная](../../README.md) · [Часть 5](README.md) · [Часть 4](../4-checks/README.md) · [§15. HTTP/3 и QUIC →](15-http3-quic.md)</sub>

Большинство разборов «как детектят прокси» молча предполагают IPv4. В 2026-м это уже неполная картина: у жилых провайдеров и мобильных операторов IPv6 часто включён по умолчанию, а у прокси — часто только IPv4. Получается вторая семья адресов, которая живёт своей жизнью.

## Чем IPv6 отличается для нашего разбора

- **Нет NAT.** Адрес устройства виден целиком (с точностью до /64-префикса), а не спрятан за одним IPv4.
- **/64 на абонента.** Префикс часто выдаётся один на подключение, и все устройства за ним делят одну подсеть. Антифрод может кластеризовать по /64: RFC 7721 §4 прямо предупреждает, что префикс может «использоваться для корреляции активности хоста независимо от того, как сгенерирован IID».
- **Приватные адреса.** SLAAC с временными IID (RFC 8981, заменивший RFC 4941) ротирует суффикс, но префикс остаётся; Windows при этом может использовать стабильный, семантически непрозрачный IID для постоянного адреса — он тоже коррелируется.
- **MSS = MTU − 60.** Для IPv6 заголовок на 20 байт больше: при MTU 1500 MSS = 1440, а не 1460 ([§4](../2-network/04-mss-mtu.md)).
- **Hop Limit вместо TTL.** Арифметика та же, значения по умолчанию те же (64/128), но поле называется иначе и в JA4T-подписях учитывается не всегда.
- **Нет IP ID** в привычном виде — часть p0f-признаков для IPv6 просто отсутствует; p0f поддерживает IPv6, но с ограничениями (длина extension-заголовков не считается), а Satori в открытом виде разбирает только IPv4.

## Как возникают утечки

Главный сценарий: **туннель несёт только IPv4, а клиент — dual-stack.** Тогда:

1. Браузер по Happy Eyeballs (RFC 8305) предпочитает IPv6, если он доступен; для сайтов с AAAA-записью соединение может уйти напрямую по IPv6, мимо IPv4-прокси.
2. WebRTC собирает ICE-кандидаты по обеим семьям: IPv6-кандидат с реальным адресом может уехать в STUN, даже если HTTP идёт через IPv4-прокси.
3. QUIC ходит по UDP и может пойти напрямую по IPv6, пока TCP-трафик идёт через прокси ([§15](15-http3-quic.md)).
4. DNS: AAAA-запросы могут уходить к резолверу провайдера, а не через туннель.

Итог: сайт видит **IPv4 от прокси** и **IPv6 от вас**. Это не «мягкий сигнал» — это прямое противоречие между слоями, такое же, как WebRTC-утечка.

## Что смотреть в тестах

- **`/ip` → IPv6 Leak Test.** Есть ли IPv6-адрес; совпадает ли его ASN/гео с IPv4; не отличается ли страна.
- **`/webrtc`.** Есть ли IPv6-кандидат; совпадает ли он с HTTP-IPv6.
- **`/dns`.** Резолверы по IPv6 — того же провайдера/региона, что exit, или домашние?
- **`test-ipv6.com`.** Показывает, видят ли вас по IPv6 вообще, и есть ли «IPv6 без IPv4»/«IPv4 без IPv6».
- **Сравнение `/64`.** Если у «разных» профилей один и тот же /64 — это один абонент, даже если IPv4-адреса разные.

В эталонном прогоне IPv6 есть и согласован: он виден и в `/ip`, и в `/webrtc`, и в DNS-резолверах; ASN/гео совпадают с IPv4. В антипримере IPv6 `n/a` — то есть профиль «Windows в США» существует только в IPv4, что само по себе не приговор (у части провайдеров IPv6 нет), но обедняет картину.

## NAT64, 464XLAT и мобильные сети

Мобильные операторы всё чаще делают IPv6-only с трансляцией: 464XLAT (RFC 6877) и NAT64 (RFC 6052). Для детекта это значит:

- IPv4-адрес может быть синтетическим/разделяемым, а реальная идентичность — в IPv6-префиксе.
- Гео IPv4 и IPv6 могут не совпадать (разные базы, разные PoP).
- «Мобильный» профиль без IPv6 при живой мобильной сети — подозрительно; мобильный профиль с IPv6 — норма.

## Что делать

1. **Туннелировать IPv6 через тот же exit.** Либо `allowed-ips` в туннеле включает `::/0`, либо IPv6 отключён на хосте — но отключение само по себе артефакт (у живой Windows/macOS IPv6 обычно включён), и Happy Eyeballs начнёт вести себя иначе.
2. **Проверять обе семьи на каждом прогоне**, а не только IPv4.
3. **Сверять ASN/гео IPv4 и IPv6** — они должны указывать на один регион.
4. **Не игнорировать /64.** Если антифрод кластеризует по префиксу, смена IPv4 внутри одного /64 ничего не даёт.
