# §6. Скорость и объём: экономика и полоса

<sub>[Главная](../../README.md) · [Часть 2](README.md) · [← §5](05-rtt.md) · [Часть 3. Браузер →](../3-browser/README.md)</sub>

Антифроду не нужен спидтест. Он видит пропускную способность своих собственных ассетов: сколько байт вытянул клиент, за какое время, с какими паузами и ретраями.

- **Симметрия и потери.** Датацентр — ровная полоса, ноль потерь, стабильный RTT. Жилой канал — «пила», просадки вечером, потери. Мобильный — скачки при переключении RRC-состояний.
- **Невозможная скорость.** UA говорит «мобильный Android, 4G», а клиент устойчиво тянет 500 Мбит/с → у оператора такого нет. Или наоборот: «гигабитный домашний интернет», а потолок 20 Мбит/с стабильно на всех запросах — где-то узкое горло.
- **Слишком ровно.** Throughput ограничен окном и RTT: `полоса ≈ окно / RTT` (bandwidth-delay product). Прокси с большим окном и низким RTT выдаёт «идеально ровную» полосу — у живого абонента так не бывает.
- **Объём.** Антифрод считает байты на сессию и сравнивает с сегментом: сколько данных «обычный» пользователь тянет за визит. Residential-прокси с трафиком по гигабайтам — экономически невыгодно, и это тоже фича в модели.
- **Ретрансмиты и reordering.** Через цепочку прокси характерен повышенный reordering и ретрансмиты. Пользователь этого не видит, сервер видит.

## Формула, которая объясняет «ровную» полосу

```
BDP = bandwidth × RTT        (сколько байт «в пути»)
полоса ≈ window / RTT        (потолок одного соединения)
```

Отсюда два следствия:

1. **Большое окно + маленький RTT = подозрительно ровная скорость.** Если окно `65535`, а RTT 1 мс, потолок одного потока ~65 МБ/с; датацентр его легко держит, жилой канал — нет.
2. **Маленькое окно + большой RTT = «медленный» профиль.** `MSS 1336` и RTT 559 мс в туннеле ([§4](04-mss-mtu.md)) дают низкий потолок даже на быстром канале: страница грузится рывками, и это видно по таймингам ресурсов.

## Что видно в наших прогонах

- **Эталон.** `TCP RTT 47 мс`, но Client Hints на `/client-hints` показывают `RTT 1400`, `downlink 1.35`, `ECT 3g`: Chrome Network Quality Estimator считает сеть плохой. Стек совпал, качество — нет. Это само по себе не «детект прокси», но объясняет, почему «идеальная подпись» не гарантирует «незаметный профиль».
- **Антипример.** `TCP RTT 161 мс ±60.6`, exit в Токио, клиент — в другой точке: медленно, рвано, с джиттером. Это уже похоже на цепочку/шлюз, а не на домашний канал.
- **Туннель.** `RTT 559 мс ±119` при `MSS 1336`: обфускация и туннель добавляют задержку. Такой профиль «живёт», но медленно.

Числа в этом разделе — **порядок величины, а не калибровка**. Скорость зависит от канала, нагрузки, CDN и времени суток; антифрод сравнивает не с таблицей, а с распределением по своим пользователям.

### Источники

- BDP и window/RTT — RFC 7323 (window scaling); Microsoft — [TCP/IP performance tuning](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-tcpip-performance-tuning).
- Network Information API — [MDN: `NetworkInformation`](https://developer.mozilla.org/en-US/docs/Web/API/NetworkInformation) (`rtt`, `downlink`, `effectiveType`; Chrome отдаёт ту же оценку в Client Hints как `Sec-CH-RTT`/`Sec-CH-Downlink`/`Sec-CH-ECT`).
- BrowserLeaks `/client-hints`, `/tcp`; ретрансмиты/reordering — [RFC 5681](https://www.rfc-editor.org/rfc/rfc5681) (congestion control).
